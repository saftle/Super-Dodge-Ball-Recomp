# tools/tas — TAS-integrated automated testing

Shared-input differential harness: one TAS drives both the MesenCE oracle and
the cycle backend, then diffs to first divergence (liveness → state → image).

## Vectors (`tas/`)

Third-party works: the `.bk2`/`.fm2` files below are tool-assisted
speedrun movies by their credited authors (via TASVideos, shared for
emulator replay with credit). They are test data, not covered by this
repo's license (see `LICENSE.md`); keep author credits intact and link
movie pages rather than re-hosting.

* `tas/vectors/sdb_4976.bk2` — TASVideos #4976 (ShesChardcore & Dasrik, BizHawk
  2.8, 19692 frames, hardest difficulty). Headerless MD5 matches our ROM
  (`6e44871b462ce90c99d9a9a8fff637a8`). Download: `tasvideos.org/4976M`
  → "Download (.bk2)" → inner zip entry is the real `.bk2` → place at
  `tas/vectors/<name>.bk2`.
* `tas/sdb_4976.tas.json` — canonical frames (button mask bits
  `A=0x80 B=0x40 SELECT=0x20 START=0x10 UP=0x08 DOWN=0x04 LEFT=0x02 RIGHT=0x01`),
  generated by `bk2_to_tas.py`. First Start at frame 11 (matches
  `oracle_dump.lua` Start@11-12 convention).
* `tas/vectors/sample_smb2_warp.fm2` — parser test vector only (SMB2 Japan
  8-1 warp, 1016 frames, savestate-anchored → converts but not harness-
  runnable; movie author credited in-file as `Invariel`). No USA Dodgeball `.fm2` exists on TASVideos (only `.fcm`
  #742 / `.bk2` #4976); manufacturing one = FCEUX `Tools → Convert FCM`
  on the #742 `.fcm` (`fceux --convert`), sync not guaranteed.

## Tools

| File | Purpose |
|---|---|
| `bk2_to_tas.py` | `.bk2` (inner zip) → canonical `tas.json` |
| `fm2_to_tas.py` | `.fm2` (FCEUX text/binary logs, RLDUTSBA) → canonical `tas.json` |
| `input_to_tas.py` | the project's own `tas/vectors/*.input` → canonical `tas.json` |
| `mesen_tas.lua` | MesenCE player + full capture (input in `inputPolled`) |
| `run_tas.py` | Runs both sides into `tas/runs/<name>/`, writes `run.json` |
| `diff_tas.py` | First-divergence report (liveness → state → images) |
| `watch_tas.py` | Watch the TAS in the cycle backend's own window (`--virtual-pad`) |
| `watch_mesen.py` / `watch_mesen.lua` | Watch the TAS in the MesenCE GUI (playback only, hands P1 back at the end) |
| `tas_watch.lua` | Who-writes probe under the TAS (addrs → frame/value/writing PC; `PRGLOG=1` resolves banked PCs) |

## Capture surfaces

* Mesen (`mesen/`): per-frame `mesen_state.jsonl` (regs, `$0100/$0106/$0107/$0168`,
  scroll/vram/tmp/wt, cycles, input echo) + `mesen_nmi_log.txt`; at stride:
  `.ppm` screenshot (raw P6 — extension is honest), `.ram/.chr/.nt/.pal/.oam/.ciram.bin`,
  `.meta.txt` (live CHR offsets via `convertAddress` + mapper keys).
* Cycle (`cyc/`): `frames.bin` CYCFRAME-v2 log (per-frame CPU RAM, CIRAM,
  32-B palette indices, OAM, picture indices; `--frame-log-at mesen` aligns
  records to Mesen's frame end), `miss.txt` (uncompiled-seed lines),
  `shots/shot_*.png` (`--shot-every`), `cyc.log`.

## Usage

```bash
python3 tools/tas/run_tas.py --tas tas/sdb_4976.tas.json --frames 400 --out tas/runs/r400
python3 tools/tas/diff_tas.py tas/runs/r400
# long runs: --shot-stride 10; side skip: --skip-mesen / --skip-cyc
# --no-build reuses the existing cycle binary (default reconfigures +
# rebuilds build-cycle/ when the ROM or src/game.toml are newer than it)
```

### Replaying our own vectors

`input_to_tas.py` exists because the oracle could only replay speedrun movies,
which is backwards: the `tas/vectors/*.input` files are the runs we most want an
oracle for. It expands a state-change vector into the flat per-frame mask array
`mesen_tas.lua` wants, holding each state to the next line and padding the tail.

```bash
python3 tools/tas/input_to_tas.py tas/vectors/sdb_bar.input \
    --out tas/vectors/sdb_bar.tas.json --frames 700
python3 tools/tas/run_tas.py --tas tas/vectors/sdb_bar.tas.json \
    --frames 700 --out tas/runs/bar700
```

Verified against `tas/vectors/sdb_bar.input` on **0 differing frames of effective
input out of 1200**. The two schedules do not read identically —
`run_tas.py`'s `emit_schedule` drops no-op steps such as a repeated `472 LEFT`
immediately after `471 LEFT` — which is why the check compares the expanded
per-frame input rather than the text.

This is what research.md §27 needs, to attribute the pan judder to either the game
or this engine; `mesen_tas.lua` already logs scroll and OAM per frame in
`mesen_state.jsonl`.

### Recorded playthroughs, and the three-way vocabulary

There are three input formats in this repo and they are easy to confuse:

| thing | written by | replayed with | used for |
|---|---|---|---|
| `.input` vector | `--record-input`, or hand-written | `nes_game --input FILE` | headless runs, and `--virtual-pad` in a **window** |
| `.tas.json` | `bk2_to_tas.py` / `fm2_to_tas.py` / `input_to_tas.py` | `run_tas.py` (both hosts) | the MesenCE oracle differential |
| `--virtual-pad` file | SDL controller names, one per change | windowed `nes_game --virtual-pad FILE` | replaying a recorded vector **in a window** |

**Why the third one exists.** A recorded vector replays faithfully *headless* and
*unfaithfully* in a window, or rather the other way round: the window and the
headless host do not run the same guest state (research §26 — frames 0-3 match,
frame 4 diverges), so anything about the presented picture must be reproduced in
a window. `--virtual-pad` drives the window's real input path from a schedule, and
two windowed runs of one schedule are byte-identical, so a played session is
reproducible that way.

To convert, map the NES names to SDL's controller names (the ones
`SDL_GameControllerGetButtonFromString` accepts — `a`, `b`, `x`, `back`, `start`,
`dpup`, `dpdown`, `dpleft`, `dpright`; note it is `dpright`, **not** `right`):

```bash
sed -e 's/\bA\b/a/g' -e 's/\bB\b/x/g' -e 's/\bSELECT\b/back/g' \
    -e 's/\bSTART\b/start/g' -e 's/\bUP\b/dpup/g' -e 's/\bDOWN\b/dpdown/g' \
    -e 's/\bLEFT\b/dpleft/g' -e 's/\bRIGHT\b/dpright/g' \
    tas/vectors/sdb_bar.input > tmp/bar.vpad
```

**`Player1Source` must be 2 for this.** Player 1 is the keyboard and player 2 the
controller, so a `--virtual-pad` replay with `Player1Source = 1` sends every
press to a controller nobody is holding and the guest sits at the title screen —
which looks exactly like "the feature does nothing". Check the `sdbc` camera
trace: a real match shows `cam=128`-ish by frame 600 and a stuck run shows
`cam=0`.

### Watching instead of diffing

```bash
python3 tools/tas/watch_tas.py           # cycle backend window, full movie
python3 tools/tas/watch_mesen.py         # MesenCE window, full movie
```

Both need a desktop display (don't wrap them in `xvfb-run`). Add
`--frames N` for a short check, `--no-exit` (watch_tas) to keep the window
open. Neither is a verification path — `run_tas.py` + `diff_tas.py` is.
`watch_tas.py` builds `build-cycle` windowed if the binary is currently a
headless one.

**Known limits**: the full movie diverges from every non-BizHawk player at
the match tipoff (frame ~474) — see `docs/research.md` §22. Watching
therefore shows the run until tipoff and then a game that is not the
recorded one; the inputs still execute exactly as written.
`watch_tas.py` notes 9 opposing-dpad frames (first at 5619) that the
windowed bindings cancel to neutral; headless/`--input` and Mesen play
both bits.

## Gates (in order, stop at first red)

1. Liveness: cycle logged frames == N, exit 0.
2. State (primary cross-side signal): CYCFRAME snapshots (CPU RAM, CIRAM,
   palette indices, OAM) byte-compared to Mesen bin dumps, joined on
   video-frame index. No stack masking: the cycle CPU pushes real return
   addresses, so the stack page must match too. Sprite entry-0 mirror bytes
   (`$3F10/$3F14/$3F18/$3F1C`) masked — hardware mirrors them to the
   backdrop, Mesen exposes the mirror, the cycle palette RAM keeps stale
   power-on bytes (upstream model, rendering unaffected).
3. Images (informational only): cross-renderer RGB always differs by palette
   emulation (cycle NTSC-signal palette vs Mesen). `compare_frames.py`
   quantizes through the cycle renderer's palette — same-renderer pairs are
   strict; cross-renderer pairs are rough. Frame 0 is black
   warmup, title from frame 1; gate images only post-boot.

## Honesty proof (2026-10-02, c30/c30b)

* Cycle A/A: `frames.bin` byte-identical across repeat runs. Oracle A/A
  (Mesen state + NMI logs, bins, PPMs identical under pinned settings).
* Red path: boot frames diverge on real modeling gaps (power-on palette,
  uninitialized CIRAM) and the diff names exact bytes — the gate reports,
  it doesn't rubber-stamp.

## Known limits

* Full 19k TAS artifacts scale with stride — use `--shot-stride 10+` and
  `--frame-log-frames` thinking for long runs (runs are gitignored).
* Join on video-frame index (cycle frame / mesen `f`), never wall-clock.
* Unseeded runs execute partly on the cycle interpreter (still bit-exact,
  just slower); `--miss-log` seed lines feed future `cycle_seed_file` runs.
